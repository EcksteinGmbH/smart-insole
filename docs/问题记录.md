## 详细记录

### ISS-001 `imu_set` / `imu_get` 字段名与 API 文档不一致
- **严重度 / 状态**：高 / 已解决
- **现象**：App 按《API 文档 V1.0.0》发送 `acc_sleep_thresh`、`acc_sleep_after_s`，旧固件读的是 `acc_wake_thresh`、`acc_sleep_after`，设置不生效，却返回 `"err":"0"`。响应里也缺少 `acc_sleep_after_s`。
- **证据**：出厂固件自检 19/25（`logs/ble_selftest_oldfw.txt`）。
- **处理记录**：
  - 2026-10-09：`main/src/protocol.c` 改为读文档字段名，旧字段名作为回退；响应键改为 `acc_sleep_after_s`；回显实际生效的阈值。烧录后自检 34/34（`logs/ble_selftest_newfw.txt`）。

### ISS-002 字段值为数字类型时固件崩溃重启
- **严重度 / 状态**：高 / 已解决
- **现象**：请求里写 `"id":0`（数字）而不是 `"id":"0"` 时，`valuestring` 为 NULL，`strtoul(NULL)` 导致崩溃重启。
- **处理记录**：
  - 2026-10-09：新增 `json_to_ul()` / `json_to_f()`，字符串和数字都能解析。`selftest --robustness` 通过，设备保持连接。

### ISS-003 USB 口看不到应用日志
- **严重度 / 状态**：中 / 已解决
- **现象**：控制台只配置在 UART0，USB-Serial/JTAG 上只能看到 bootloader 输出。
- **处理记录**：
  - 2026-10-09：sdkconfig 开启 `CONFIG_ESP_CONSOLE_SECONDARY_USB_SERIAL_JTAG=y`、`CONFIG_USJ_NO_AUTO_LS_ON_CONNECTION=y`，烧录后 `tools/capture.sh` 能看到完整日志。

### ISS-004 BLE 开启时自动 light sleep 永不生效
- **严重度 / 状态**：高 / 待决策
- **现象**：启动日志
  `W BLE_INIT: 32.768kHz XTAL not detected, fall back to main XTAL as Bluetooth sleep clock`
  `W BLE_INIT: light sleep mode will not be able to apply when bluetooth is enabled.`
- **根因**：
  - sdkconfig 按「有外部 32 kHz 晶振」配置：`CONFIG_RTC_CLK_SRC_EXT_CRYS=y`（sdkconfig:1123）、`CONFIG_BT_CTRL_LPCLK_SEL_EXT_32K_XTAL=y`（sdkconfig:760），硬件实际没有这颗晶振。
  - 启动时回退到主晶振；又因 `CONFIG_BT_CTRL_MAIN_XTAL_PU_DURING_LIGHT_SLEEP` 未开，BT 控制器创建 `NO_LIGHT_SLEEP` 电源锁（IDF `components/bt/controller/esp32c3/bt.c:1296-1314`）。
  - 结果：PM + tickless idle 的省电配置实际无效，芯片最多只进 modem sleep。
- **影响**：续航。官方典型值（ESP32-C3，NimBLE power_save 例程）：modem sleep 约 12 mA，light sleep（主晶振）约 2.3 mA，light sleep（32 kHz 晶振）约 140 µA。均未在本板实测。
- **方案**：
  - A（只改配置）：`CONFIG_BT_CTRL_LPCLK_SEL_MAIN_XTAL=y` + `CONFIG_BT_CTRL_MAIN_XTAL_PU_DURING_LIGHT_SLEEP=y`，RTC 时钟改 `CONFIG_RTC_CLK_SRC_INT_RC=y`。
  - B（改硬件）：加 32 kHz 晶振，收益最大。
  - 两种方案都需要验证 BLE 连接稳定性、30 ms IMU 推送，并用电流表实测。
- **待决定**：是否先做方案 A；是否评估方案 B。
- **来源**：Espressif 文档 MCP 查询（low-power-mode-ble 指南、NimBLE power_save README），已与本地 v5.4.1 源码核对。

### ISS-005 静止时陀螺仪掉电，BLE 帧中陀螺值冻结
- **严重度 / 状态**：高 / 待决策
- **现象**：静止时 IMU 进入芯片 inactivity 模式（`main/src/app_lsm6d.c:145`，`LSM6DS3TR_C_XL_12Hz5_GY_PD`）：加速度降到 12.5 Hz，陀螺仪掉电。固件仍按 33 Hz 发 IMU 帧，帧里的陀螺值停在最后一次读数，而且不为零。
- **证据**：`logs/ble_stream_newfw.txt` 中 168 帧的陀螺值完全相同（如 IMU0 gx=2082.5 mdps）；`imu_get` 的 freq 读回约 13 Hz。
- **影响**：App 可能把冻结的陀螺值误判为脚在转动；BLE 带宽被重复数据占用。
- **方案**（任选，前两种涉及协议变更）：
  1. inactive 时帧内陀螺值置 0；
  2. 帧内加状态位（例如用 LEN 之后一个字节标记 inactive）；
  3. inactive 时降低发帧频率或暂停发送。
- **待决定**：与 App 工程师商定方案。

### ISS-006 低电量自动休眠失效
- **严重度 / 状态**：高 / 待处理
- **现象**：电量低于 0%、未接 USB 时应倒计时进入深睡，实际不会进入；开机即 0% 也不会休眠（规格要求开机 0% 时闪灯后休眠）。
- **根因**：`main/src/app_wakeup.c`
  - `:119` state 0 检测到低电量后置 `state = 2`，但低电量倒计时写在 `case 3`（`:153`），永远进不去；
  - `case 1`（`:125`）末尾缺 `break`，会落入 `case 2`（`:146`）。编译器也报了 `-Wimplicit-fallthrough`。
- **方案**：低电量分支改为 `state = 3`；`case 1` 末尾加 `break`；重新核对状态机与规格表中三种休眠路径。

### ISS-007 电池分压比与电压阈值和规格不符
- **严重度 / 状态**：高 / 待确认
- **现象**：
  - 规格：GPIO2 = 0.75 × Vbat；满电 4.1 V（ADC 3.075 V），0% 为 3.67 V，3.60 V 休眠。
  - 代码：`components/bat/bat.c:160` 按 `2 * avg_mv`（即 0.5 分压）计算；`main/bsp.h:39-40` 为 3.6 V 到 4.05 V。
  - 另外，3.075 V 超过 ESP32-C3 ADC 在 11 dB 衰减下的量程（约 2.5 V）。
- **证据**：实测接 USB 时读到 4.105 V、100%，看上去合理，说明硬件可能实际就是 0.5 分压。
- **待确认**：硬件实际分压电阻值，确认后再修改规格表或代码。

### ISS-008 蓝牙设置的参数掉电不保存
- **严重度 / 状态**：中 / 待处理
- **现象**：规格要求通过蓝牙设定的参数（IMU 阈值、休眠时长、使能等）自动保存，断电不丢失。代码只调用了 `nvs_flash_init()`（`main/main.c:110`），从未读写 NVS。
- **方案**：在 `imu_set` 成功后写 NVS，启动时读回；需确定要持久化的字段清单。

### ISS-009 未实现 MCU 内部温度读取
- **严重度 / 状态**：低 / 待决策
- **现象**：规格要求可通过蓝牙读取 MCU 内部温度，API 文档 V1.0.0 中没有对应接口。
- **待决定**：是否作为 `info_get` 的新增字段（例如 `temp`）。需先与 App 侧约定，再更新 API 文档。

### ISS-010 LED 指示与规格不符
- **严重度 / 状态**：中 / 待确认
- **现象**：
  - 开机：规格要求红灯闪 3 次；代码闪的是绿灯（`main/src/app_led.c:28`）。
  - 进入休眠：规格要求绿灯闪 3 次；代码闪的是红灯（`main/src/app_wakeup.c:252`）。
  - 规格表把 GPIO8 / GPIO10 同时写成充电芯片的 CHARGER / STDBY 状态脚，代码把它们当作 LED 输出来驱动。
- **待确认**：GPIO8 / GPIO10 的硬件连接方式（MCU 驱动 LED，还是充电芯片驱动），确认后再改闪灯逻辑。

### ISS-011 IMU 中断唤醒被取消，与规格不符
- **严重度 / 状态**：中 / 待确认
- **现象**：当前版本（目录名「取消imu唤醒」）只注册 GPIO3（USB）为深睡唤醒源（`main/src/app_wakeup.c:140`）。IMU 长时间静止进入深睡后，只能插 USB 或按复位唤醒。规格要求 IMU INT2 中断唤醒并自动重连蓝牙。
- **待确认**：
  - 取消 IMU 唤醒是有意的产品决定，还是临时措施；
  - 规格表 V0.3 前后矛盾：GPIO4 接的是 IMU1 还是 IMU2 的 INT。

### ISS-012 I2C 1 MHz 超出 IMU 支持的 400 kHz
- **严重度 / 状态**：中 / 待处理
- **现象**：`components/i2c/include/i2c.h:11` 为 `I2C_MASTER_FREQ_HZ 1000000`，LSM6DS3TR-C 的 I2C 最高支持 400 kHz（快速模式）。目前通信正常，但没有余量，温度或线长变化时可能出错。
- **方案**：改为 400 kHz，再验证 IMU 读数频率仍满足 52 Hz × 2 颗的需求。

### ISS-013 默认休眠阈值文档写 150 mg，实际 125 mg
- **严重度 / 状态**：低 / 待决策
- **现象**：`main/src/app_lsm6d.c:88`、`:152` 设置 150 mg，寄存器每档 62.5 mg（±4 g 量程），实际生效 125 mg；API 文档写「开机默认 150」。
- **待决定**：把默认值改为 125 或 187.5，或在 API 文档注明阈值按 62.5 mg 一档量化。

### ISS-014 API 文档缺少 IMU 数据流说明
- **严重度 / 状态**：中 / 待处理
- **现象**：API 文档 V1.0.0 只描述了 JSON 命令，没有 0xFFF4 IMU 二进制流的帧格式、发送周期和 MTU 要求，App 端缺少解析依据。
- **方案**：把开发文档 §3 的帧格式（`55 AA LEN + 2×6×float32 + SUM`，30 ms，MTU ≥ 55）补进 API 文档，连同 ISS-005、ISS-013 的说明一起发给 App 工程师。

### ISS-015 `motor_set id="3"` 响应只反映电机 0
- **严重度 / 状态**：低 / 待处理
- **现象**：`id="3"` 同时启动三个电机，但响应只取 `motorx[0]` 的状态（`main/src/protocol.c:320`）。
- **方案**：保持现状并在文档中注明，或在响应里分别返回三个电机的状态（属于协议变更，需与 App 侧约定）。

### ISS-016 固件没有计步 / 步态识别
- **严重度 / 状态**：— / 待决策
- **现象**：固件只上传原始 IMU 数据，振动反馈完全由 App 下发 `motor_set` 触发。
- **待决定**：步态识别放在固件端还是 App 端；如果放在固件端，需要定义识别结果的上报格式和自动反馈规则。

### ISS-017 编译警告与测试代码被编进固件
- **严重度 / 状态**：低 / 待处理
- **现象**：
  - 编译警告 13 个：未使用变量、`ADC_ATTEN_DB_11` 已弃用（`components/bat/bat.c:59`、`:80`）、`app_wakeup.c` fall-through（即 ISS-006）。
  - `main/CMakeLists.txt:4` 使用 `GLOB_RECURSE`，`main/test/*.c` 和 `ble_v2.c` 也被编进固件。
- **方案**：清理警告；确认测试代码是否需要，不需要就排除出编译。
